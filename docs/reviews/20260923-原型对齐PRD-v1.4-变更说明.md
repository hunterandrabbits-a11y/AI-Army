## 一、变更概览

| 项目 | 变更前 | 变更后 |
| --- | --- | --- |
| 原型版本号 | v57 · 全局夜间模式与账号配置提示 | v65 · 低消卡片主次对调 + 完成百分比（无空态）、看板 2 卡、充值记录 3 列 |

## 二、逐项变更

### 2.1 「消费明细」升级为「电力账户」

对应 PRD-v1.4 §5.1 电力账户字段、§6.4 客户侧展示口径。

- 弹窗入口、标题、关闭按钮 aria-label 全部由「消费明细」改为「**电力账户**」。
- 概览区为 **2 张卡片 + 1 行轻量文案**：

| 卡片 / 文案 | 当前取值 | 说明 |
| --- | --- | --- |
| 可用电力值 | `6,800` | 深色主卡。**不展示**「账户余额，可为负、可透支」副文案 |
| 本周期已消耗 | `1,000` | **v63 主次对调**：主数字为动态消耗量，小字标注「本期最低消耗 1,200」，内嵌进度条 83% |
| 有效期至 | `2027-06-15` | 一行轻量文案，**不展示**剩余天数，也**不提示**到期后冻结 |

- **删除「冻结电力值」卡片**：账户被冻结时系统以弹窗阻断使用，客户根本进不到本页面，展示冻结值没有受众。账户模型仍保留该字段（PRD-v1.4 §5.1），只是客户侧不展示。
- 新增样式：可用电力值为负时数字转为警示色（`.consumption-summary-card.is-balance b.is-negative`），浅色 `#ffb4a8`、深色主题同步适配。
- 顶栏余额与弹窗余额共用 `syncPowerValueUI()` 同步，**不再对负值做 0 截断**（PRD-v1.4 §5.2）。

### 2.2 低消由「四格周期模块」改为「进度条」（v63 主次对调、v64 补进度值）

对应 PRD-v1.4 §4.1 / §4.2 周期口径、§6.4 低消展示口径。

**变更前**：概览卡下方有一整块 `#consumption-cycle` 周期卡，四格展示「本周期起始日 / 剩余天数 / 已消耗电力值 / 月低消」，缺口时追加一条橙色补差预告条。

**变更后**：整块周期卡删除，低消改为月最低消耗卡片内的一条**进度条**。**v63 又对卡片内部的主次做了一次对调**：

| 元素 | v61 口径 | **v63 口径** |
| --- | --- | --- |
| 卡片标题 | 本账户月最低消耗 | **本周期已消耗** |
| 主数字（大号） | `1,200`（固定的月低消） | **`1,000`（本周期已消耗，随明细数据动态变化）** |
| 进度条宽度 | `83%`（1,000 ÷ 1,200） | `83%`（不变） |
| 小字（左端） | 本周期已消耗 1,000 · 还差 200 | **本期最低消耗 1,200** |
| 小字（右端） | —（无进度读数） | **已完成 83%**（v64 补出） |

对调的理由：客户打开这一页最想知道的是「我这个周期消耗到哪了」，而原设计把**固定**的目标值 `1,200` 放大、把**动态**的进度读数缩成小字，主次颠倒。对调后大数字随消耗明细实时变化，一眼可读。

- 进度条按「本周期已消耗电力值 ÷ 本期最低消耗」填充，`aria-valuenow` / `aria-valuemax` 同步；已达本期最低消耗时进度条转为完成态（绿色）。
- **进度值直接可读（v64）**：原设计只有一条进度条，填充比例只能靠目测。现在进度条下方一行做成两端对齐——**左端**「本期最低消耗 1,200」、**右端**「已完成 83%」，构成「目标—完成度」的对照。百分比与进度条**取自同一次计算**，不会出现读数打架；**超额消耗时一并截断为 100%**（进度条已填满，读数不再超过 100%）。
- **「还差 Y」补扣预告删除**：原小字里的「还差 200」本质是周期末补扣金额的预告，与 PRD-v1.4 §6.4「不设补差预告」的立场相抵。本次一并去掉——卡片只回答「消耗到哪了」（主数字）与「目标是多少」（小字），缺口由进度条未填满的部分直接可读。周期末的补扣仍以一条「31天最低消耗补扣」费用记录出现在消耗明细里。
- **客户侧不再展示周期日期**：本周期起始日与剩余天数退出客户页，只保留在运营后台（PRD-v1.4 §10.2）作为对客解释依据。
- **低消不设空态（v65 删除）**：原 `monthlyMinimum` 为空时隐藏进度条与百分比、小字转「本账户未设置月最低消耗」的分支**已整段删除**。月最低消耗是行业消耗模版的**必配项**、由运营随模版一并提供，不存在未配置的账户（PRD-v1.4 §2.4 / §6.4），故进度条与完成百分比**恒展示**。
- **关键口径**：周期内「已消耗」只累计**落在本周期区间内**的业务消耗，**不含低消补扣本身**（PRD-v1.4 §4.2 / §12.3 第 17 条）。展示的周期为**周期 1（2026-07-28 ~ 08-27）**，即明细数据所在的周期，故进度条与下方明细表讲的是同一个周期，可当场互相验算。
- **单条记录的电力值取自单价表**：`consumptionBusinessRecords()` 的 `power` 取自 `consumptionUnitPower[岗位]`（主号 / 副号 50、客服 10、矩阵 2），**不是**明细行里的 `power` 字段。验证时曾按 `row.power` 断言「新增一条 100 电力记录应 +100」，实测 +50，核对后确认是断言写错、实现无误。

### 2.3 新增「充值记录」第二本账

对应 PRD-v1.4 §2.7 充值记录。

- 明细区顶部新增账本切换 tab：「**消费明细**」（默认）/「**充值记录**」。
- 充值记录为 **3 列**：到账时间 / 到账电力值 / 备注。
- **已删除的记录项与列**：
  - 五个记录项——实收金额、优惠电力值、抵扣负值、计入可用余额、状态。删除原因是充值记录对客户侧的用途是「到了多少电力值」，现金口径（收了多少、让利多少、抵了多少负值）属商务侧信息，留在客户可见的表里既增加理解成本、又暴露优惠力度。状态列删除后由「记录不可改、错误走冲正」承接。
  - 一列——操作人。登记人属运营内部信息，客户只需看到「到了多少」；该字段仍记录、仍在运营后台展示（PRD-v1.4 §10.1 / §10.6）。**两侧列口径由此正式分开**：客户侧 3 列，后台展示完整记录项。
- **备注改为系统按固定规则自动生成**：正常充值固定为「补充电力值」；本次到账电力值中有抵扣账户负值的，写作「补充电力值，抵扣 N 电力值」（N 为本次抵扣掉的负值）。
- **客户侧只读**：无编辑、无撤销入口，仅保留「导出记录」按钮。
- 示例数据 3 条，**覆盖「正常充值」与「抵扣负值」两种入账**：

| 到账时间 | 到账电力值 | 备注 | 充值前 | 充值后 |
| --- | --- | --- | --- | --- |
| 2026-07-28 10:20:00 | +1,000 | 补充电力值 | 0 | 1,000 |
| 2026-09-23 10:20:00 | +5,000 | **补充电力值，抵扣200电力值** | **−200** | 4,800 |
| 2026-09-24 14:35:00 | +2,000 | 补充电力值 | 4,800 | 6,800 |

- **抵扣链路如何成立**：周期 1 只充了 1,000，业务消耗 1,000 后归零，周期末又补扣 200 → 账户转负 **−200**（这正是 PRD-v1.4 §5.2「余额可为负、可透支」的体现）。09-23 客户充值 5,000，到账电力值**先抵扣这 200**，实际计入可用余额 4,800——备注里写的就是这笔抵扣额。第 3 条充值发生在余额已转正之后，备注回到纯「补充电力值」，与前一条形成对照。
- 首条到账时间 **2026-07-28** 即低消周期起点（PRD-v1.4 §2.7）。
- **连带影响（已在 PRD 侧记录）**：实收金额删除后，§6.3「优惠实现」原以「实收金额 / 优惠电力值 / 优惠率」为骨架的算法失去输入，已整节重写为「优惠体现为到账电力值高于 1:1 基准，系统不单独记录优惠额度、不计算优惠率」；§9.3 导出不再含实收金额口径列；§13 待确认 5 定稿关闭，新增待确认 9（运营侧如何核对现金口径）。

### 2.4 消耗明细改为「全部 + 四个岗位」两层视图

对应 PRD-v1.4 §9.1 / §9.2。

- 岗位 tab 最前新增「**全部**」并设为默认选中（原先默认落在「主号获客专家」）。
- **「全部」视图只用 5 列**（2026-09-24 修订，原为公共 6 列）：

  `扣费时间 / 数字员工 / 扣费账号 / 电力值 / 扣费备注`

  **去掉「计费对象」的原因**：该列承载的是线索标识与作品标题，属岗位内部的业务对象细节，不同岗位的行之间不可比；「全部」视图的用途是跨岗位横向对比。
- **各岗位视图 = 公共 6 列 + 该岗位业务列**（公共列仍含「计费对象」）：

| 岗位视图 | 公共列 | 追加业务列 |
| --- | --- | --- |
| 主号获客专家 | 6 列（含计费对象） | 客户信息、联系方式、留资时间、城市、车型、预算、客户意向（7 列） |
| 副号获客专家 | 6 列（含计费对象） | 同上 7 列 |
| 客服专员 | 6 列（含计费对象） | 无 |
| 矩阵视频发布专员 | 6 列（含计费对象） | 无 |

- **低消补扣是账户级费用**，不属于任何岗位：只在「全部」视图出现，且其 **数字员工 / 扣费账号两列展示「—」**；在四个岗位视图中均不出现。
- **「计费对象」列承载差异字段**，采用主行 + 副行两段式：
  - 线索计费：主行为线索标识 `L202608270924`（由扣费时间派生，保证同一条线索在各视图可对齐）。
  - 作品计费：主行为作品名，副行为「任务 · MM/DD HH:mm」，例如「配置对比：买车前先看这项任务 · 08-27 08:00」。
- **电力值按 1:1 以负数展示**（如 `-50`、`-200`），**任何视图都不出现单价列与取价来源列**——对齐 PRD-v1.4 §8.4 验收 8 的展示层与计费层解耦要求。
- 分页保持每页 8 条；「全部」视图共 33 条记录 / 5 页，**低消补扣作为最新一条落在第 1 页第 1 行**（2026-09-24 修订，原为落在末页）。

### 2.6 刊例价口径改为电力值（1:1）

对应 PRD-v1.4 §2.3。

- `POWER_RATE` 由 `10` 改为 `1`，`powerPriceLabel()` 将 `¥50` 渲染为 `50 电力值`。
- 四个岗位刊例价（全行业统一，仅展示）：

| 岗位 | 刊例价 | 计费口径 |
| --- | --- | --- |
| 主号获客专家 | 50 电力值 / 有效线索 | 按有效线索计费 |
| 副号获客专家 | 50 电力值 / 条 | 按有效线索计费 |
| 客服专员 | 10 电力值 / 转化线索 | 按转化线索计费 |
| 矩阵视频发布专员 | 2 电力值 / 次发布 | 按次发布计费 |

- 客服专员**不再按自然日计费**（原 `¥3 / 有效回复`）。
- 四个岗位的 `priceNote` 统一改为「**按业务结果计费**：…，**实际结算以平台配置为准**」，满足 PRD-v1.4 §8.1 的计费提示要求；同时**不出现**「实际结算价可能与展示价不同」这类差异说明文案（§8.4 验收 8）。
- 前台恒展示刊例价，**不展示月最低消耗**、不展示 L1/L2 取价来源。

### 2.7 雇佣依赖：余额改为非阻断提示

对应 PRD-v1.4 §8.2 雇佣依赖。

- `requirementsForEmployeeIds()` 的余额项新增 `blocking: false`，文案改为：

  > 当前可用电力值 6,800，余额不足不阻断雇佣，请联系运营人员充值

- 门禁判定函数 `firstRunRequirementsReady()` 改为 **`filter(item => item.blocking !== false)`** 后再判定——只有阻断项参与「能否雇佣」。
- 检查项渲染 `renderFirstRunChecks()` 新增 `is-notice` 态：图标为 `·`、按钮为**禁用的「不阻断雇佣」**，与阻断项的 `!` 图标区分。
- **移除余额项的「查看消费明细」跳转按钮**——PRD-v1.4 §8.2 明确不提供「去充值」跳转。
- PRD 脚本内的 `prdEmployeeRequirements()` / `prdHireBlockers()` 同步改造，雇佣流程文案改为「确认抖音营销授权状态后即可开始矩阵发布；**余额不足不阻断雇佣**。」，汇总文案收敛为「请完成抖音营销授权。」
- 结果：**抖音营销授权是唯一阻断项**。

### 2.8 岗位更名

对应 PRD-v1.4 §11.4。

## 三、数据口径自洽性

### 3.1 账户对账（PRD-v1.4 §6.5 验收 12）

> 账户可用电力值 = 全部充值记录**到账电力值**合计 − 全部费用记录扣减电力值合计

| 项 | 金额 |
| --- | --- |
| 到账电力值合计 | 1,000 + 5,000 + 2,000 = **8,000** |
| 业务消耗合计 | 1,000 |
| 低消补扣合计 | 200 |
| 费用合计 | **1,200** |
| **可用电力值** | 8,000 − 1,200 = **6,800** ✅ |

> 注：对账用的是「到账电力值」列（含用于抵扣负值的部分），不是抵扣后计入可用余额的部分。本次数据中 09-23 那笔到账 5,000、其中 200 用于抵扣，两者相差 200——正是这个差额让「抵扣」这条链路在账面上可验算。

### 3.2 低消补扣的可验算性（本次修订的核心目的）

明细中唯一一条补扣记录为 **2026-08-27 23:59:59 / -200 / 31天最低消耗补扣**，落在「全部」视图**第 1 页第 1 行**，与概览区进度条同屏，可当场互相验算：

| 项 | 值 | 来源 |
| --- | --- | --- |
| 本期最低消耗 | 1,200 | 低消卡片小字 / 补扣行 |
| 周期内业务消耗合计 | 1,000 | 低消卡片主数字 + 明细中 32 条业务记录求和 |
| **周期末补扣** | **200** | 1,200 − 1,000 = 200 ✅ |

业务消耗 1,000 的构成：主号获客专家 10 条 × 50 + 副号获客专家 8 条 × 50 + 客服专员 9 条 × 10 + 矩阵视频发布专员 5 次 × 2 = 1,000。

> 低消卡片展示的周期与明细表展示的数据**同属周期 1**，因此「卡片上的 1,000 / 1,200 / 83%」与「明细里的 200 补扣」是同一件事的两种呈现，不需要客户自行换算周期归属。

### 3.3 时间线自洽

| 时间 | 事件 | 账户余额 |
| --- | --- | --- |
| 2026-07-28 | 首次充值 1,000 电力值（**低消周期 1 起点**） | 1,000 |
| 2026-08-25 ~ 08-27 | 周期 1 业务消耗 1,000 | **0** |
| 2026-08-27 23:59:59 | 周期 1 末补扣 200 → 余额转负 | **−200** |
| 2026-09-23 | 充值 5,000，先抵扣 200，计入 4,800 | 4,800 |
| 2026-09-24 | 充值 2,000 | **6,800** |

> 客户页展示的是**周期 1 的结算时点**：低消卡片读作「本周期已消耗 **1,000**」+「本期最低消耗 1,200」+ 83% 进度条，明细表最后一行正是那笔 200 的补扣，充值记录第 2 行则是这 200 被抵扣掉的那一刻——三处讲的是同一笔 200。周期 2（2026-08-28 ~ 09-27）不在客户页展示，只存在于运营后台。

### 3.4 首条充值时间即低消周期起点

`accountPower.firstRechargeAt = 2026-07-28` 与充值记录首条到账时间一致。周期 1 = 2026-07-28 ~ 2026-08-27（31 天），即客户页进度条所展示的周期。

## 五、验证方式与结果

### 5.1 验证方法

将原型剥离内联 base64 资源后生成临时副本，注入 localStorage 预设与断言驱动脚本，用无头 Chrome 渲染并回读 DOM：

```
Chrome --headless --disable-gpu --no-sandbox \
       --user-data-dir=<tmp> --virtual-time-budget=45000 \
       --dump-dom http://127.0.0.1:8791/.tmp-verify.html
```

驱动脚本在页面加载后逐项点击、读取 DOM 并输出 `PASS / FAIL` 清单，最后将文档 DOM 替换为 `<pre id="diag">` 以便回读。

### 5.3 已知限制

- 无头验证的临时文件（`.tmp-verify.html`）仅用于本地验证，不属于交付物，验证结束后已删除。
- 「不出现月最低消耗」这类**负向断言**在目标元素为空时会空过，因此每条负向断言都配了一条正向断言交叉确认。
- 断言中读取 `textContent` 时，相邻行内元素之间不会自动插入空格（如 `有效期至` 与 `2027-06-15`），驱动脚本对这类断言统一用 `\s*` 容错，避免把渲染正确误判为失败。
